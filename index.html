Refresh Opportunity Scoring

A reproducible, client-held-out content review queue built on anonymized FlyRank search data.

Abstract

This project asks which content pages should be inspected first when an editor has limited refresh capacity. I used the bundled FlyRank anonymized starter release, one row per content item, with trailing 90-day search and engagement measurements. I compared transparent rules, logistic regression, a shallow decision tree, and a random forest using the same client-held-out split and ranking metrics. The random forest measured ROC AUC 0.750, average precision 0.618, and Precision@50 0.740, versus 0.627, 0.468, and 0.240 for the baseline. This is directional decision support for human review, not proof that refreshing causes traffic recovery.

Problem

Editors need a repeatable way to choose which pages to inspect first. The output is a ranked queue with reason codes and a human-review action; it never publishes or edits content automatically.

Data and methodology

The analysis uses the 30,000-row anonymized starter release covering 32 pseudonymized clients. Rows without impressions and content younger than 90 days were excluded. The label is trend_direction == down. Label-derived fields, identifiers, provider metadata, and last-30-day outcome fields were excluded from features. A random forest with seed 42 was evaluated with complete clients held out.

Ranked recommendations

  1. Inspect the highest-scored pages first.
  2. Verify decline evidence, search intent, accuracy, ownership, accessibility, and context.
  3. Use stale-update or thin-content codes as review prompts, not automatic prescriptions.
  4. Re-evaluate with a fresh labeled window before claiming improvement.

Limitations and honest framing

This is an association with an observed decline proxy, not a causal study. It does not predict Google's algorithm, guarantee future traffic, or show that a refresh will produce recovery. Missingness, fixed snapshot timing, client mix, and small denominators limit generalization. Human review is mandatory.

Reproducibility

Run the notebooks from the repository root with Python 3.11 and requirements.txt. See ML-08 model, ML-09 validation, and ML-10 action playbook. The queue is exported to work/outputs/content_action_queue.csv.
